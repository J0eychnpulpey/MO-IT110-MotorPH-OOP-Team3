KI-22 verification: popup windows are modal dialogs now (2026-10-31)

Environment: javac 21.0.12.1 · Windows · branch fix/ki22-modal-popups (based on main @ 4e40acc)

WHAT WAS WRONG
The five popup screens were javax.swing.JFrame instances created with
setDefaultCloseOperation(EXIT_ON_CLOSE), none of them modal, and every parent built a
brand-new instance on each button click. A close request aimed at a child window therefore
called System.exit() on the JVM that also hosts the main window, and nothing stopped the user
from opening the same screen eight times.

BEFORE (main @ 4e40acc, probe: CloseBugProbe.java)
    LeaveForm: class=LeaveForm extends=JFrame resizable=false modal=false
    LeaveForm.getDefaultCloseOperation() = 3  (3 = EXIT_ON_CLOSE, 1 = HIDE_ON_CLOSE, 2 = DISPOSE_ON_CLOSE)
    Dashboard.getDefaultCloseOperation() = 3
    frames created from 3 button clicks: 4 (same object? false)
    now dispatching WINDOW_CLOSING on ONE child LeaveForm (the main window stays open)...
    >>> JVM EXIT: something called System.exit(), so the whole app is gone
    exit code: 0

The probe never made a window visible: the exit came from Frame.processWindowEvent, not from a
human clicking anything. That is why the defect reproduces identically in Eclipse, in VS Code
and from the terminal - the IDE is not part of the cause. (In a VS Code debug session the JVM
dying just looks like "debug session ended"; Eclipse prints the same thing as "terminated".)

WHAT CHANGED
  LeaveForm.java          extends javax.swing.JDialog, ctor (Frame owner, String employeeNumber), DISPOSE_ON_CLOSE
  ChangeCredentials.java  extends javax.swing.JDialog, ctor (Frame owner, String employeeNumber), DISPOSE_ON_CLOSE
  Form.java               extends javax.swing.JDialog, ctor (Frame owner), DISPOSE_ON_CLOSE
  LeaveManagement.java    extends javax.swing.JDialog, ctor (Frame owner), DISPOSE_ON_CLOSE, navigation swap
  LeaveApproval.java      extends javax.swing.JDialog, ctor (Frame owner), DISPOSE_ON_CLOSE, navigation swap
  Dashboard.java          LeaveForm and ChangeCredentials are built with the dashboard as owner
  MainMenu.java           LeaveManagement and Form are built with the main menu as owner
  each <screen>.form      JFrameFormInfo -> JDialogFormInfo, defaultCloseOperation 3 -> 2

Modal dialogs also settle the duplicate-window complaint without a singleton field: while one
is open the parent window is blocked, so the button that opens it cannot be clicked again.
Leave Management and Pending Leaves replace each other, so they now hand the owner up one level
and dispose themselves BEFORE opening the modal child - a modal child blocks inside
setVisible(), which would otherwise leave the old screen open behind it.

EXIT_ON_CLOSE is now set only on the top-level windows that are supposed to end the app:
LoadingScreen, LandingPage, Login, LoginHR, Dashboard, MainMenu.

MOUSE-FREE CLOSE TEST ON THE RUNNING APP (the third symptom, after the fix)
Date: 2026-10-31 22:47 Asia/Taipei
App: launched from Eclipse (javaw.exe pid 7272), Dashboard open as employee 1
Why: the Cancel button calls dispose() directly and therefore proves nothing - the defect
     lived in the window-manager close path (WM_CLOSE -> WINDOW_CLOSING -> default close
     operation). Alt+F4 does nothing on an undecorated dialog, so the close request was sent
     straight to the popup's HWND, which is exactly what the taskbar's "Close window" sends.

    WATCHING pid=7272 for class=SunAwtDialog (up to 240s)
    POPUP FOUND hwnd=1246678
    POSTED WM_CLOSE ok=True
    APP_ALIVE=YES
    POPUP_GONE=True

Reading: the popup accepted the close request and disappeared (POPUP_GONE), and the JVM that
hosts the main window kept running (APP_ALIVE=YES). Before the fix the same message reached
EXIT_ON_CLOSE and took the whole application down.
